# Бронирование переговорной

Тестовое задание: интерфейс бронирования переговорной комнаты в течение рабочего дня (09:00–18:00).

## Запуск

```bash
npm install
npm run dev
```

- `npm run lint` / `npm run lint:fix` — ESLint
- `npm run format` / `npm run format:check` — Prettier
- `npm test` / `npm run test:watch` / `npm run test:coverage` — тесты (Vitest)
- `npm run build` — проверка типов и сборка

Нужен Node.js 20.19+ или 22.12+ (требование Vite 8). Все проверки запускаются в GitHub Actions на каждый пуш.

## Что умеет

- выбор даты (стрелки, календарь, кнопка «Сегодня»);
- расписание дня сеткой по 30 минут: свободные, занятые и прошедшие слоты;
- создание брони кликом по свободному слоту или кнопкой «Новая бронь»;
- редактирование (кнопкой в списке или кликом по занятому слоту) и удаление с подтверждением.

## Бизнес-правила

Все правила лежат в `src/utils/validation.ts` и используются в двух местах: в форме (сразу показываем ошибку, а занятое/прошедшее время отключено в селектах) и в мок-сервере, который клиенту не доверяет и проверяет всё заново.

- время в пределах 09:00–18:00, `start < end`, длительность 30 минут – 2 часа;
- пересечения запрещены, касание границ (10:00–11:00 и 11:00–12:00) — нет;
- нельзя бронировать прошедшее время: на сегодня прошедшие слоты недоступны, на прошедшие даты форма не открывается. Текущее время обновляется раз в 30 секунд, так что слоты «гаснут» без перезагрузки;
- при редактировании бронь не конфликтует сама с собой;
- уже начавшуюся бронь нельзя редактировать, закончившуюся — удалять.

## Конфликт со стороны сервера

Бэкенда в задании нет, поэтому `src/api/bookings.ts` — мок на `localStorage` с задержкой 400 мс. Ответы: 400 — невалидные данные, 404 — брони нет, 409 — время уже занято.

Если сервер вернул 409, форма остаётся открытой со всеми введёнными данными, показывается понятное сообщение, а расписание перезагружается — новая чужая бронь сразу видна. Если бронь удалили, пока её редактировали (404), форма переключается в режим создания, и данные можно сохранить как новую бронь.

Воспроизвести конфликт можно двумя способами:

1. включить переключатель «Имитировать конфликт на сервере» внизу страницы — перед сохранением «другой сотрудник» займёт выбранное время;
2. открыть приложение в двух вкладках и забронировать одно и то же время.

## Тесты

81 тест на Vitest и Testing Library, покрытие около 92%. Время в тестах заморожено (10.01.2030, 10:05), поэтому результат не зависит от дня запуска.

- `utils/*.test.ts` — бизнес-правила и работа со временем, включая все границы;
- `api/bookings.test.ts` — мок-сервер: статусы 400/404/409, сервер не доверяет клиенту;
- `hooks/useBookings.test.ts` — загрузка, ошибки, повтор, гонка ответов при быстрой смене даты;
- `App.test.tsx` — пользовательские сценарии целиком, на настоящем мок-сервере. «Другая вкладка» имитируется записью в хранилище, пока форма заполнена.

### Проверенные граничные случаи

- брони, касающиеся границами (10:00–11:00 и 11:00–12:00), — допустимы; любое пересечение, вложение или накрытие — конфликт;
- ровно 30 минут и ровно 2 часа — можно; 15 минут и 2,5 часа — нельзя; 09:00 и 18:00 — крайние допустимые значения;
- начало в текущую минуту — можно, минутой раньше — нельзя; прошедшая дата — нельзя;
- название из одних пробелов не проходит; невалидная форма не отправляется на сервер;
- редактирование не конфликтует с самой бронью, но конфликтует с остальными;
- идущую встречу нельзя изменить, но можно удалить; закончившуюся — ни то, ни другое (и сервер это тоже проверяет);
- день, занятый до конца, — кнопка создания недоступна;
- 409 от сервера — понятное сообщение, список обновлён, форма и введённые данные на месте, можно выбрать другое время и сохранить;
- 404 при редактировании (бронь удалили в другой вкладке) — форма переходит в создание, данные сохраняются;
- 404 при удалении — ошибка и обновлённый список; двойной клик по «Удалить» отправляет один запрос;
- ответ по старой дате, пришедший после ответа по новой, игнорируется;
- ошибка загрузки показывается с кнопкой «Повторить», а при ошибке перезагрузки уже показанные брони не стираются;
- повреждённые данные в хранилище не роняют приложение;
- даты считаются в локальном часовом поясе, переходы через месяц, год и 29 февраля корректны.

## Стек и структура

React 19 + TypeScript + Vite, UI — Material UI. Бизнес-логика от UI-библиотеки не зависит: правила и мок-сервер — обычные функции без React.

```
src/
  api/bookings.ts         мок сервера
  hooks/useBookings.ts    загрузка броней на дату
  hooks/useNow.ts         текущее время с периодическим обновлением
  utils/time.ts           работа со временем и датами
  utils/validation.ts     бизнес-правила
  components/             DateSelector, DaySchedule, BookingForm, BookingList,
                          ConfirmDeleteDialog, NoticeSnackbar, DevPanel
  theme.ts                тема Material UI (русская локаль)
  test/                   настройка и хелперы тестов (*.test.ts лежат рядом с кодом)
  App.tsx                 состояние страницы и обработка ответов сервера
```
